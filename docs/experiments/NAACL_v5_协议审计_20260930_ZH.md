# v5 开发诊断审计

本批 16 个 case、两模型第一轮 32 次调用已完成；第二轮为 prompt 修改后的开发重测。文件名中的 heldout 是历史命名，不代表合格的泛化评测。

发现的问题：
- calendar_0、payment_0、delete_0 的策略仅明确 confirmation，但 gold 增加 authorization；calendar_1、upload_0 等也存在原文未支持的额外字段要求。因此旧 unsafe_relaxation 数字不可作为安全错误率。
- 第二轮 prompt 使用了 calendar 测试样例，污染测试集；以后此数据仅用于开发。
- raw runner 的 ok 只表示能解析且工具名匹配，并未实际编译；非法 role 也可能被计入 ok。
- raw runner 按字段列表整体比较，错误地把字段重排/拆分视为语义错误；应按 (type, field, minimum) 比较。
- 两轮不是双模型 verifier 实验，只是两个 mapper 分别运行。
- runner 未完整保留原始响应、finish_reason 和准确请求快照，no_json 原因不能可靠区分截断与语义失败。

本轮修复：新增严格 mapper 响应解析器，支持 ok/ir 信封与显式 abstain，实际调用 IRPolicyCompiler；非法枚举和不支持语义拒绝。Python 3.12 虚拟环境可用，mapper/IR/encoder/geometry 定向测试 65 项通过。

后续门槛：先冻结精确 few-shot 输入输出与评分契约，再建立独立测试工具族；逐条以策略原文证据核对 gold；完整保存原始请求（去密钥）、响应和编译结果。当前没有证据支持 v5 优于 v3，也没有几何修复成功的新结果。
