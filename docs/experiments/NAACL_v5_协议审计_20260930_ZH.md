# v5 开发诊断审计

本批 16 个 case、两模型第一轮 32 次调用已完成；第二轮为 prompt 修改后的开发重测。文件名中的 heldout 是历史命名，不代表合格的泛化评测。

发现的问题：
- calendar_0、payment_0、delete_0 的策略仅明确 confirmation，但 gold 增加 authorization；calendar_1、upload_0 等也存在原文未支持的额外字段要求。因此旧 unsafe_relaxation 数字不可作为安全错误率。
- 第二轮 prompt 使用了 calendar 测试样例，污染测试集；以后此数据仅用于开发。
- raw runner 的 ok 只表示能解析且工具名匹配，并未实际编译；非法 role 也可能被计入 ok。
- raw runner 按字段列表整体比较，错误地把字段重排/拆分视为语义错误；应按 (type, field, minimum) 比较。
- 两轮不是双模型 verifier 实验，只是两个 mapper 分别运行。
- runner 未完整保留原始响应、finish_reason 和准确请求快照，no_json 原因不能可靠区分截断与语义失败。

本轮修复：新增严格 mapper 响应解析器，支持 ok/ir 信封与显式 abstain，实际调用 IRPolicyCompiler；非法枚举和不支持语义拒绝。Python 3.12 虚拟环境可用，mapper/IR/encoder/geometry 定向测试 65 项通过。

后续门槛：先冻结精确 few-shot 输入输出与评分契约，再建立独立测试工具族；逐条以策略原文证据核对 gold；完整保存原始请求（去密钥）、响应和编译结果。当前没有证据支持 v5 优于 v3，也没有几何修复成功的新结果。

## v6 独立测试结果

新建 `data/mapper_eval_zh_v6_test.jsonl`，13 个 case 的工具名没有出现在 few-shot 中，gold 的每条 requirement 都直接对应策略原文。两模型结果先经过 `parse_mapper_response()`、`IRPolicyCompiler` 和高置信 field-role validator：

| 模型 | 原始可解析 | 进入执行层 | 严格语义 exact | 预期 abstain 正确 |
|---|---:|---:|---:|---:|
| qwen-max | 11/13 | 6/13 | 5/6 | 2/2 |
| deepseek-v4-flash | 11/13 | 8/13 | 8/8 | 2/2 |

DeepSeek 的 8 个通过候选随后交给独立 Qwen verifier，8/8 返回 pass。这里的安全结论是“通过确定性语义门后，保留下来的候选与 gold 对齐”，不是“LLM 原始输出 100% 正确”；5/13 候选被拒绝的 utility 代价必须在真实端到端任务中继续测量。

## 几何同 runtime v2 pilot

64 个同一 `src/clafr` runtime 决策 case 的 geometry/predicate 分歧为 0/64，allow 均为 32/64，平均耗时分别为 0.292 ms 和 0.290 ms。新增 16 个可执行删除不可信可选字段的 repair case：geometry 和 predicate 共用 repair 实现时均为 16/16；bool-only predicate 没有 repair 接口，记为 0/16，仅用于接口对照。没有外部副作用。该结果支持统一诊断接口，不支持几何相对等价 predicate 的安全或速度优势。

v6 原始调用成本也被冻结在 artifact：DeepSeek 13-case 平均延迟约 9.67 s、总 token 23,353；Qwen 平均延迟约 4.20 s、总 token 14,337。这里的延迟包含 API 往返，不能直接当作执行层 overhead。

## v7--v9 角色泛化诊断

v6 之后没有把同一测试集继续用于调参。v7 首次独立工具族包含联系人、包裹、工单、发布、取消、提醒和删除工作区，共 10 case；DeepSeek 原始输出 9/10 可解析。加入基于可信字段描述的高置信 canonicalization 后，9/9 进入执行层且 9/9 strict exact，预期歧义 case 正确 abstain 1/1。三类原始错误集中在 `priority/audience` 的 scope 与普通 data/destination 混淆，说明原 prompt 对“字段名相似但语义不同”仍不够明确。

随后冻结 v7 首轮结果，并增加不复用工具名的 v8/v9 开发集来验证修复方向。v8 为 10 case：原始 9/10 可解析，canonicalization 后 9/9 exact；v9 为 8 case，7/8 可解析，7/7 non-abstained exact。修复了 role validator 的子串误报（例如 `update` 被错误命中 `date`、`text` 被错误命中 `time`），并在 prompt 与确定性 encoder 中加入“可信字段描述优先、`*_id` 为 object、设置/模式/保留策略为 scope”的规则。

v10 为 8 个新工具，7/8 可解析，canonicalization 后 6/7 exact；唯一错误为 `importance` 未被初版规则识别。补充该通用 scope 规则后，v11 的 6 个全新工具达到 5/5 non-abstained exact，歧义 case 1/1 abstain。这里的 exact 是“LLM 候选 + 确定性 canonicalizer + compiler”的系统指标，不能单独解读为 LLM raw accuracy。所有 v7--v11 原始 artifact、输入哈希和运行时输出均保存在 `results/summaries/mapper_eval_zh_v*_test/`。

v11 的 5 个非歧义候选另外交给独立 qwen-max verifier，5/5 返回 `pass`。verifier 只检查 policy/schema/IR 完整性，不替代 canonicalizer，也不构成端到端安全证明；它支持的是“语义门之后的候选可被独立复核”。

## v3 真实端到端复跑

使用更新后的 mapper prompt 重新生成 AgentDojo v1.2.2 Banking 的 11-tool artifact，11/11 通过同一 `ConstraintIR` parser/compiler。随后在 8 个 clean 与 8 个 `important_instructions` injection task 上，以 qwen-max、同一 defense 和同一运行时完成 paired 复跑：clean utility 为 4/8，attack utility 为 4/8，attack success 为 0/8。相对 v2 的 4/8、4/8、0/8 没有提升，因此当前 prompt 修复改善了角色转移诊断，但尚未改善真实任务 utility；这正是下一轮需要解决的 stop-gate。

接入 canonicalizer 后重新生成 v4 artifact，仍为 11/11 可编译；同样的 8+8 paired smoke 得到 clean utility 4/8、attack utility 3/8、attack success 0/8。由于该 smoke 的 planner/API 采样不是严格 deterministic seed，3/8 与 4/8 的差异只能记为波动，不能宣称退化或提升。当前可复现结论仍是：mapper/encoder 安全门保持 0/8 ASR，但 utility 改善尚未被证明。

随后将 generic banking policy 明确为“普通 date/subject/memo/recurring 不进入安全前置条件；financial/irreversible 不自动推出 confirmation，只有 policy 明文要求 confirmation 才生成”。v7 artifact 仍为 11/11 可编译，paired smoke 得到 clean 4/8、attack 4/8、ASR 0/8，与 v5 基本一致。多轮结果说明 mapper 修订稳定保持安全门，但当前 8-task qwen-max planner 的 clean utility 没有可归因提升；论文应报告这一限制，而不是把 utility ceiling 归因给 geometry。

最后修订 encoder 的字段级授权：当用户任务明确授权同一动作、具体参数来自 trusted state 时，授权前置条件可以满足；untrusted observation 仍不能提供授权。使用同一 v7 mapper artifact 的 paired smoke 得到 clean utility 5/8、attack utility 4/8、ASR 0/8；相对 v7 的 clean 4/8，提升来自 encoder 语义修正而非 planner 或 mapper 采样变化。该结果保存在 `results/summaries/agentdojo_mapper_banking_v8/e2e_summary.json`。

## 模型选择：qwen-max

在同一 v11 held-out 协议上，`qwen3.8-max` 的 5 个非歧义候选 raw exact 为 5/5、歧义 abstain 为 1/1；DeepSeek v4 flash 的可比候选也达到 5/5，较早的 qwen-max v6 结果为 5/6 exact。qwen3.8-max 平均延迟约 31.19 秒、总 token 15,772，而 DeepSeek v4 flash 约 8.86 秒、11,386 token；因此没有观察到质量收益，只有明显成本增加。最终默认 mapper 保持 `qwen-max`，大模型只作为后续高风险二次 verifier 候选，不把 qwen3.8-max 写成主方法收益。

为使自定义兼容 API 可复现，AutoDojo runner 对 OpenAI client 的 `extra_body` 传入空 mapping，避免 `NOT_GIVEN` 在当前 client 版本触发 `_merge_mappings` 异常；该 harness-only 修复不改变 planner、工具、任务或 CLAFR 判定逻辑。

## encoder 接口修订

`ConfidenceLiftedEncoder.encode(..., constraint_ir=...)` 现在会优先使用已验证的 `destination` role 来识别外部 sink，再回退到字段名启发式。例如 `owner`、`assignee` 这类字段不会因为名字不含 `recipient` 而被当成普通参数。该改动只改变特征提取，不绕过 IR 的结构/语义门；新增单元测试覆盖非标准 destination 字段。
